# Results

All numbers are produced by running the **real Anyray optimizer** over the
synthetic payloads in this repo and measuring the request it returns. Two tiers:

- **Accounting** (the committed `results/*.json`) — whole-request token reduction
  at `chars / 4`, reproducible by anyone with a running optimizer: `./run.sh --all`.
  The **percentage is the number to trust** — it's confirmed against a real tokenizer
  (`tiktoken`) and the optimizer's own estimator. `chars / 4` typically makes the
  absolute token counts a conservative estimate on prose and logs, but can overcount
  on dense JSON or tool-schema content (where real chars-per-token exceeds 4).
- **Live bill** — the provider's real `prompt_tokens`, end-to-end. A real-provider
  cross-check from the Anyray stack is [below](#live-bill-cross-check), kept for
  historical reference only: it predates this edition and nothing in the repo backs
  it. A built-in `--live-bill` mode is on the [Roadmap](#roadmap).

Produced against optimizer **v0.3.201**, defaults revision 17. Every committed result
row carries the version that measured it.

### Savings by strategy (accounting tier)

Where the headline comes from — so the composition is visible, not hidden behind
one number. Four strategies carry most of it: `observation_mask`,
`context_compression`, `window_budget` and `relevance_filter` together hold ~88%
of this suite's input (34% / 22% / 17% / 15%). `observation_mask` leads on share
only because its fixture is a long agent trajectory and long trajectories are
large; one fixture is not evidence that it leads in production. That is a
property of **these fixtures**, not a measurement of production traffic — read
the rows as "what each strategy does to a representative payload", not as a
weighted forecast of a deployment's bill.

Share of input is set by fixture size, not by whether a strategy fired, so a
strategy that saved nothing would still hold its share here. Judge each row by
its own **Saved** column.

### The rows that used to read 0%

Four accounting rows scored 0% against optimizer 0.3.201 where the previous
edition (0.3.132, 2026-08-25) scored 97%, 65%, 28% and 83%. All four are fixed
here, and none of the fixes is a knob that papers over a stand-down: each row now
measures its strategy on a payload shaped the way a real client sends one. Key-fact
survival is 100% on all four.

The suite pins a strategy and measures what comes back, so a strategy that
correctly stands down and one that is broken look identical. That is why none of
these was caught by a test, and it is worth keeping in mind for the next one.

| Workload | Strategy | Then | Was | Now | What was actually wrong |
|---|---|--:|--:|--:|---|
| `4-json-array` | `context_compression` | 97% | 0% | **94%** | The 500-order dump was pasted into the user turn *behind a sentence of prose*, so `detectType` read the segment as `text`, not `json`, and the JSON crusher never ran on it. The old 97% came from `maxChars` blind-truncating a text blob, and that default went 8,000 → 0 (unbounded) in #2512. The dump now arrives as a tool result, the way a client actually delivers one; `maxArrayItems: 50` caps the array structurally and the remaining 450 orders go behind a retrieve handle. |
| `6-git-diff` | `context_compression` | 65% | 0% | **84%** | Also a retired `maxChars` default, but "same cause" was wrong: the diff *was* being shape-detected correctly all along. It simply had no budget knob that still exists. `maxDiffLines: 40` is the shape-aware one, and it beats the old byte cap (84% vs 65%) because it caps hunks rather than truncating the tail. |
| `7-codebase-explore` | `code_graph` | 28% | 0% | **27%** | Correctly diagnosed before: one user message opening with prose before the first `// ===== file =====` banner, and since #2565 the structure parser requires a source-shaped opening. The prose is now its own turn, so the file blob is parsed as the graph it is. |
| `36-stale-observations` | `observation_mask` | 83% | 0% | **95%** | The old explanation — "no mask pays for itself on the turn it fires; a single-turn fixture never collects" — was wrong on the facts. The fixture was never single-turn (15 messages, 7 completed exchanges) and its payback horizon was 2 turns, not 0. The real gate: with no context window declared, the optimizer cannot compute context pressure, so `maskAdmission` falls to its priced-mint lane, which only mints inside a *cached prefix* — and a harness calling the optimizer directly has no gateway to establish one. The fixture now declares its model's real 200k window and carries a trajectory that genuinely exceeds it, which is the condition a stale-observation mask exists for. |

Two things worth carrying forward. First, `metadata.modelContextTokens` is not
decoration: several strategies gate on context pressure, and a payload that never
declares a window can never be pressured, so they stand down no matter what the
payload holds. Second, a fixture that pastes bulk content into a user turn behind
a sentence of prose will be classified by that prose — shape detection reads the
opening bytes. Both are properties of the harness, not of the optimizer, and both
produced a 0% that looked like a strategy regression.

One limit remains, and no fixture can close it: the mask's settled-boundary mint
path needs decision pins threaded from the gateway, and a harness that calls
`/v1/optimize` directly never sends them. Rows here therefore measure the
pressure lane only.

## Does it preserve the answer?

Measured in **[QUALITY.md](QUALITY.md)**: for each workload we define the
answer-bearing key facts and check how many survive the trim. The committed,
reproducible signal is **strict substring survival**: **all 33 preserve the
answer in full** — each workload's strategy is matched to its content and its
settings tuned for strong savings while keeping every answer-bearing fact. That
check needs only the optimizer, so anyone can reproduce it. The optional
semantic-judge lane (`run_quality.mjs --judge`) has not been re-run against the
current optimizer, so no judge verdicts are committed: an old verdict describes a
differently-trimmed context, which would be worse than none. The "Answer
preserved?" column above is the demo stack's end-to-end live validation; the
quality benchmark turns it into a reproducible per-workload score. Anyray's
strategies are also **reversible** (every elided span is retrievable via
`POST /v1/retrieve`) and **fail open** (a slow/down optimizer forwards the request
unoptimized).

## Coverage

Every number on this page was produced against optimizer **v0.3.201** (defaults
revision 17). Each committed result row records the version and revision that
measured it, so a partial re-run can never quietly blend eras again — which is
what the previous edition of this page did, publishing v0.3.24 and v0.3.41 rows
in one table with nothing to tell them apart.

**[COVERAGE.md](COVERAGE.md) is the answer to "which strategies does this suite
measure?"** — 21 of the 25 registered kinds, each with its workloads, its
measured basis, and its cache flags. Four are uncovered. `audited_holdout` is not
benchmarkable here by construction: it is the unoptimized control marker, so it
transforms nothing and has no per-strategy knob to pin. The other three are
genuine gaps this suite has not caught up with: `client_prefix_compression`
(added 2026-09-04), `columnar_fold` and `repeat_factor` (both 2026-08-19).

The two most recent additions close the last measurable gaps: `43-thinking-replay`
(`thinking_trim`, on by default and previously unmeasured) and `44-prefix-churn`
(`cache_lint`, a read-only cross-turn sensor that needs two requests). Both are
scored on their own basis rather than whole-request bytes — see the guardrails
table above.

Two workloads carry environment prerequisites that change what they measure:
`37-durable-blob` needs the durable CCR tier (without it `output_externalize`
self-gates to an honest 0%), and `42-semantic-rerank-rag` needs the local MiniLM
embedder (without it the filter degrades to lexical and the answer can be ranked
out). See [VALIDATION.md](VALIDATION.md#environment-prerequisites); both were
available for the run above.

## Roadmap

- **Semantic relevance filter.** An embedding-based filter for the vocabulary-
  mismatch workloads where lexical BM25 ranks the answer lines out (see
  [QUALITY.md](QUALITY.md#why-two-arent-green)). *Partially covered now:
  workloads 32/33 carry `semanticRerank: true`, and new workload 42 adds a
  lexical-trap scenario that BM25 alone gets wrong.*
- **`--live-bill` mode in this repo.** Wire the gateway round-trip so the live tier
  is reproducible here, not just on the demo stack.
- **Latency.** Record the hook's added latency per workload (it fails open past
  `ANYRAY_OPTIMIZER_TIMEOUT_MS`, but the typical-case cost is worth publishing).
