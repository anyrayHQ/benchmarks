# Results

All numbers are produced by running the **real Anyray optimizer** over the
synthetic payloads in this repo and measuring the request it returns. Two tiers:

- **Accounting** (the committed `results/*.json`) — whole-request token reduction
  at `chars / 4`, reproducible by anyone with a running optimizer: `./run.sh --all`.
  The **percentage is the number to trust** — it's confirmed against a real tokenizer
  (`tiktoken`) and the optimizer's own estimator. `chars / 4` typically makes the
  absolute token counts a conservative estimate on prose and logs, but can overcount
  on dense JSON or tool-schema content (where real chars-per-token exceeds 4).
- **Live bill** — the provider's real `prompt_tokens`, end-to-end. A real-provider
  cross-check from the Anyray stack is [below](#live-bill-cross-check); a built-in
  `--live-bill` mode is on the [Roadmap](#roadmap).

### Live validation — hosted gateway (2026-07-08 audit)

Full per-strategy live run through the production gateway (`gateway.anyray.ai`,
Claude Sonnet 4.6 answers, Claude Opus 4.8 judge; every request is visible as a
trace in the Anyray console). All 29 workloads, each sent as baseline (optimize
off) and optimized (strategy pinned, transformed by optimizer v0.3.41), answers
compared by the judge. Real provider bill across the suite: **443,344 →
134,655 prompt tokens (−70%)**. Verdicts: **24 PASS / 3 MARGINAL / 1 FAIL /
1 N/A** (the N/A is `context_quality`, a read-only diagnostic).

- MARGINAL (answer intact, secondary detail drift): `1-access-log` (96% saved),
  `16-test-run` (79%), `33-synonym-gap-logs` (61%).
- FAIL — `8-long-session` (`window_budget`, 72% saved): a **baseline-parity
  failure**, not an optimization loss. The judge's own rationale records that
  the baseline answer (full, un-optimized context) makes the identical error
  the optimized answer makes (billing-first vs the session's orders-first
  recommendation), while the crop demonstrably preserves the answer-bearing
  turns (strict facts 100%, payload judge PASS). The workload's `maxTokens`
  pin was moved 8000 → 24000 after the 8000 crop failed the live judge
  outright.

## 2026-07-08 full audit — what changed and why

The whole suite was re-run fresh against optimizer **v0.3.41** (committed
numbers above; the previous baseline was v0.3.24). Findings:

1. **Fresh-input protection reshaped 8 payloads.** v0.3.41 refuses to digest
   tool output the model hasn't seen yet (tool results after the last
   assistant turn are the model's live input; digesting them measurably
   backfired on real traffic). Eight payloads authored as single-turn
   "trailing tool dump" (15, 17, 18, 27, 28, 29, 30, 32) measured 0% on
   v0.3.41 for the wrong reason — the instrument, not the strategy. They are
   now **history-shaped** (an assistant digest turn after the dumps, the
   original question repeated verbatim as the live turn), matching how the
   strategies operate on real multi-turn traffic. Lesson recorded: the final
   user turn must repeat the question **verbatim** — a paraphrase shifted
   `relevance_filter`'s semantic rerank enough to drop the answer chunks on
   `32-vocab-mismatch-rag`.
2. **`code_graph` stays the chosen code strategy.** Head-to-head on the five
   code workloads, `code_skeleton` saves 8–11 pts more but destroys key facts
   (4/6 and 3/6 survival on the multi-file traces); `code_graph` keeps 100%
   everywhere. The default (`code_graph` on, `code_skeleton` retired) is
   confirmed.
3. **Pipeline order is validated — no re-order.** Composite runs of the full
   default pipeline over all 24 accounting workloads under alternative orders
   (generic-compaction-first; code-specialists-before-`relevance_filter`)
   produce identical results: with the shipped default params each workload's
   bulk is claimed by exactly one strategy, and `relevance_filter`'s
   conservative defaults (`keepChars=32000`) never steal the code
   specialists' input. Order stands as shipped.
4. **One default changed upstream:** `code_graph` `minChars 400→200,
   minBodyLines 4→2` (anyray repo: `optimizer.config.json` + `codeGraph.ts`).
   The 4-line body floor made the strategy decline compact sources and file
   reads, leaving them to generic line filters. With 200/2 the full default
   pipeline's composite savings rise **32.8% → 34.0%** with **98/98 key facts**
   preserved, and the live judge passes all five code workloads at exactly
   these values (16–70% saved). All 903 optimizer unit tests pass with the
   new defaults.

## Does it preserve the answer?

Measured in **[QUALITY.md](QUALITY.md)**: for each workload we define the
answer-bearing key facts and check how many survive the trim. The committed,
reproducible signal is **strict substring survival**: **all 24 preserve the
answer in full** — each workload's strategy is matched to its content and its
settings tuned for strong savings while keeping every answer-bearing fact. A
**committed Claude Opus 4.8 judge**
(each verdict recorded in its `by` field) adds a semantic read and confirms
**24 PASS / 0 MARGINAL / 0 FAIL**. The "Answer preserved?" column above is the demo
stack's end-to-end live validation; the quality benchmark turns it into a
reproducible per-workload score. Anyray's
strategies are also **reversible** (every elided span is retrievable via
`POST /v1/retrieve`) and **fail open** (a slow/down optimizer forwards the request
unoptimized).

## Roadmap

- **Semantic relevance filter.** An embedding-based filter for the vocabulary-
  mismatch workloads where lexical BM25 ranks the answer lines out (see
  [QUALITY.md](QUALITY.md#why-two-arent-green)).
- **`--live-bill` mode in this repo.** Wire the gateway round-trip so the live tier
  is reproducible here, not just on the demo stack.
- **Latency.** Record the hook's added latency per workload (it fails open past
  `ANYRAY_OPTIMIZER_TIMEOUT_MS`, but the typical-case cost is worth publishing).
